## 1. 对赛题要求的判断

项目已经具备自然语言输入、结构化计划、DAG 编译、动态风险、权限网关、分级确认、Mock Bank Core 执行和审计的闭环。支持部分口语表达、联系人解析、预置跨场景组合及受限澄清续问。

但不能据此宣称已完整实现自由自然语言需求理解、通用上下文解析和任意跨场景任务规划。六场景工具覆盖不等于语言表达覆盖；当前更准确的定位是「支持限定表达与预置组合的可信银行智能体原型」。风险评级由确定性引擎完成，模型不决定授权。自主执行指在既有策略约束内推进任务，黄色/红色操作仍需确认/MFA。全部金融结果仍为 Mock Bank Core 模拟结果。

代码依据：

- `backend/aegisbank_api/config.py`：默认 `planner_mode=rule`；另有 `llm/auto` 模式。
- `planning/rule.py`、`planning/intents.py`、`scenarios/*`：关键词/正则及按优先级首个命中的场景规则；部分参数从联系人簿、订阅列表解析。
- `planning/contracts.py`：PlanningRequest 尚无通用会话、实体记忆或对话修订结构；ExecutionPlan 支持步骤与依赖，尚无显式条件契约。
- `trust/clarification.py`、`main.py`：已支持绑定用户与角色、10 分钟有效、单次消费的澄清续问，以原指令加补充文本重新规划；修改/取消类补充会被拒绝，要求重新提供完整指令。
- `planning/llm.py`：模型候选写操作种类/数量须与规则参考计划一致，关键参数须有来源；该保护约束了模型拓展新表达和组合的空间，不能直接移除。
- `planning/compiler.py`、`scheduler.py`：已有 Schema、工具、依赖、环检测、哈希、上游结果引用和受控调度；结构合法不能证明用户语义已被完整保留。

## 3. 建议定位：可验证的金融语义规划

让用户看见「系统如何理解需求、每个关键参数来自哪里、哪些信息尚不确定」，并证明原意被完整保留。沿用信任执行链，在其前方增加可检查的语义层：

```text
用户表达 + 有界会话状态
  → 金额/日期等确定性规范化（保留原文位置）
  → 结构化语义候选（意图、实体、条件、否定、顺序、缺失项）
  → 实体与参数来源验证 + 必要澄清
  → 任务完整性验证 + DAG 编译
  → 既有动态风险 / 网关 / 确认 / ToolExecutor / 审计
```

候选槽位除值之外，记录原文片段、轮次、解析方式、事实来源与验证状态。模型自报 confidence 不作为授权依据；当前规则固定的 confidence 也不能解释为实测正确率。语义完整性验证须结合独立规范化、契约校验和评测，不能只让同一个模型自证正确。

## 4. 分阶段建议与验收

### P0：先消除错误理解产生的写计划

- 建立统一金额规范化，覆盖千分位、中文数字、万/千/块、币种与分位精度，保留原始片段；不支持或有歧义的格式必须澄清，不能截取部分数字。金额运算使用 Decimal 或整数分。
- 在条件与多意图尚未完整支持前，识别这类请求并返回说明性澄清，不得悄悄降成无条件或部分写计划。
- 审视默认卡片/账户/订阅目标；写操作不得因解析失败或数据读取失败而随意选用演示对象。用户明确建立的默认选择也须可见、可撤销、执行前复核。
- 将本次反例及变体变为自动回归，覆盖预览、执行入口和候选校验；对不支持的语义断言无写副作用，而不只检查返回文案。

验收：1,500 正确解析或明确拒绝；未知条件绝不丢失；多任务不能仅执行首个命中写操作。确认机制不能替代语义正确性。

### P1：把自然语言理解做成独立、可评测的模块

- 设计版本化 SemanticFrame 候选契约：意图列表、实体槽位、金额/时间、肯定/否定作用域、条件、顺序、未覆盖片段与澄清需求。
- 使用模型处理口语和组合语义，确定性组件验证金额、日期、实体、字段与来源；规则保留为基线与安全回退。
- 金融实体从当前用户的受控事实中解析；歧义给候选选项，模型猜测不得成为已验证事实。新增工具查询继续经过网关与执行链。
- 用「语义契约与授权动作一致性」逐步替代「必须与旧规则写操作计数一致」的能力上限；迁移前保留现有防护，经过对照评测后再切换。

验收：对六场景中没出现过的同义表达给出语义等价计划；未知对象和不明确金额必须澄清；否定局部动作不误伤独立查询。

### P2：实现有边界的上下文与纠错

- 服务端维护会话/任务草稿、实体候选、缺失槽位与最近查询结果，绑定用户与角色，设 TTL、版本及并发冲突控制。
- 支持「给妈妈转钱 → 五百」「刚才那张卡」「不是500，改成300」；只继承明确可用的槽位，不能继承上一笔授权。
- 修改尚未执行的计划时生成新 plan_hash，使旧确认失效并重新评级；已执行的动作不得被改写，转入新操作或受控补偿。
- 澄清问题优先解决影响操作对象、金额、方向的歧义，避免要求用户整句重说；不确定性不能用模型自信分数掩盖。

验收：多轮补全与修改正确；隔离跨用户、过期上下文和并发草稿；旧确认不能执行新计划；重复回复不产生重复动作。

### P3：从预置组合走向有约束的组合规划

- 从完整意图列表编译工具步骤，验证每个动作、否定、条件和顺序均有对应处理；不能用优先级首个命中替代完整规划。
- 建立有类型的结果引用及条件表达式白名单，禁止 eval 或任意模型代码；支持条件为真/假/未知的明确处理。
- 条件依赖的余额等事实经受控读取，在写入时复核；涉及并发资金变动的条件需在 Mock Bank Core 事务中保证一致性，不能只依赖早先的余额快照。
- 审核前展示完整计划；确认后按既有网关、风险与 ActionEnvelope 执行，保留暂停、失败、补偿与不可逆语义。

验收：「先分析账单，再取消我选中的订阅，然后查询余额」步骤完整；条件不满足时零写入；未获选定或确认时零写入；注入、未知结果与中途撤权不能促成额外动作。

### P4：将能力变成可展示、可量化的亮点

- 前端展示理解摘要、参数来源、缺失信息、可编辑草稿、任务 DAG 与执行状态；模型解释与银行事实分开呈现。
- 建立首批建议不少于 300 条的人工标注语料，覆盖六场景、口语、中文金额、否定、时间、指代、纠错、条件、多意图及恶意输入。按语义模板/表达家族划分开发集和保留集，避免近似改写泄漏。
- 对照评估现有规则、现有 LLM 模式和新方案，固定工具目录与 Mock 数据。真实模型实验需单独记录模型版本和配置；模拟响应测试不能算作模型理解准确率。
- 报告意图/槽位正确率、关键参数精确匹配、完整计划语义正确率、多轮任务完成率、漏步骤率、条件保留率、澄清必要性、非必要澄清率，以及延迟和调用成本。DAG 应按依赖/行为等价评估，不只比 JSON 字符串。
- 建议初始目标：保留集支持范围内完整计划语义正确率 ≥95%；安全反例集未经授权/参数错误/条件丢失的写执行为 0。两者必须同时满足，不能靠全部拒绝提高安全成绩。这些是待基线评测后复核的目标，不是现有成绩，也不是生产安全保证。

展示主线：口语需求 → 一次关键澄清 → 参数来源 → 跨场景 DAG → 必要确认 → Mock 执行和审计；另展示修改金额导致旧确认失效，以及条件不满足时不转账。

### 7.1 核对范围与判定口径

- 输入：2026-10-27 用户反馈的 6 条 P1 级口语表达（见 7.2）。
- 对照：§4 P1 的 4 条建议与验收、§4 P0 的金额/澄清承诺、[NLP 待办](NLP-BACKLOG.md)任务 1、3，以及任务 2、4、5、6、7、8、9 的阶段边界。
- 判定口径：
  - **计划层覆盖**：已有具名意图/槽位/事实来源/验收，按计划文字即可直接实现并判定。
  - **部分覆盖**：已有上位原则（如「实体从当前用户受控事实解析」「金额/日期规范化」），但缺本反馈所需的具名意图、槽位、事实字段、消歧规则或验收用例。

- 阶段边界：跨轮指代、缺失槽位续问、执行前修订属于 P2；通用多意图、条件与任意 DAG 属于 P3；300 条语料与完整效果报告属于 P4。若「那个涨价的订阅」必须依赖上一轮列表或对话指代才能确定，则归 P2；若能仅凭当前用户订阅事实中的价格变化记录或风险标记唯一定位，则可作为 P1 单意图处理。该边界需在实现前明确。

### 7.3 对 P1/P1 相关待办的具体修订

以下为对 P1 及 P1 相关待办的修订建议，只写入本节，不直接改写 §4 或 `NLP-BACKLOG.md` 中既有的 P0/P1 原文；实施时应另立任务并按本节验收。

#### 7.3.1 SemanticFrame 的意图与实体槽

当前 `planning/contracts.py` 只有 `PlanningRequest` 与 `ExecutionPlan`，没有独立的语义草稿。P1 已提出版本化 SemanticFrame，但需要把六条反馈所需的槽位写成可验收字段：

- 顶层至少包含：`frame_version`、`intent_ids[]`、`entity_slots[]`、`amount_mentions[]`、`time_mentions[]`、`negation_scopes[]`、`conditions[]`、`order[]`、`uncovered_fragments[]`、`clarification`、`status`。
- 每个实体槽至少记录：`slot`、`entity_type`、`raw_text`、`span`（起止位置）、`normalized_value`、`fact_source`、`fact_id`、`verification_status`。`verification_status` 至少区分 `verified` / `ambiguous` / `missing` / `unsupported`。
- 六条反馈的最小槽：
  - 挂失：`target_card`（尾号/卡号后缀/唯一卡）+ `action=report_card_lost`。
  - 账单：`account`（可默认但必须可见）+ `period=last_month` + `category=餐饮` + `aggregation=spend_total`。
  - 转账：`payee`（`ACC-2002` 或联系人）+ `amount`（Decimal/分）+ `currency=CNY`。
  - 还款日：`target_card` + `repayment_day=18`，不得生成 `amount` 槽。
  - 联系人转账：`contact`（规范化姓名/别名）+ `amount=200`。
  - 订阅：`subscription`（`subscription_id`）+ `target_evidence`（`price_increase` / `risk_flag`）+ `action=cancel_subscription`。
- `status` 至少含 `needs_clarification`、`draft`、`ready_for_compile`；Planner 不得直接产出 `completed`（见 7.3.6）。
- 未覆盖片段必须显式保留，不能被模型或规则静默丢弃；关键槽位缺来源时不得标记为 `verified`。

#### 7.3.2 联系人别名与卡片尾号事实源

- 联系人事实至少包含：`contact_id`、`user_id`、`canonical_name`、`aliases[]`、`phone`、`account_id`、`status`、`source`。当前联系人表只有 `name`/`alias` 精确匹配字段；需在事实层或规范化层支持「我妈/老妈/母亲 -> 妈妈」等常见关系别名，并记录命中的事实来源。
- 解析优先级建议：手机号精确匹配 -> 姓名/别名精确匹配 -> 受控别名规范化后精确匹配；不把模糊相似或模型猜测直接升级为 `verified`。多匹配或零匹配必须 `needs_clarification` 并给出候选（零匹配给可见原因），不得静默选择或猜测。
- 卡片事实至少包含：`card_id`、`masked_number`、`account_id`、`status`、`repayment_day`、`is_default`。尾号 `9902` 与 `CARD-9902` 都应唯一解析到同一事实；写操作（挂失、改还款日等）只能使用唯一、已核验的卡片。
- 默认卡只能在用户明确建立、展示且可撤销时用于只读默认；写操作不得因解析失败回退到 `CARD-8821` 等演示对象。若没有唯一卡，计划应为澄清，步骤为空。

#### 7.3.3 阿拉伯数字 + 中文单位的金额规范化

- P1 继续复用 P0 金额解析器，不新增第二套金额规则；但必须把「阿拉伯数字 + 中文数量单位」的单列形式加入 P0 解析器回归和 P1 评测集，例如：`1万`、`1.5万`、`2千`、`1亿`、`1万元`、`1万块`。`1万` 必须与 `一万元` 等价为 `10000.00 CNY`。
- 保留完整词元和原文 span；不得截断为 `1` 或 `1000`。`1万5`、`一万五` 这类省略写法按 P0 既有原则视为歧义并澄清；`1,500` 仍为 `1500`。金额运算使用 Decimal 或整数分，不使用二元浮点。
- 对同一请求出现多个金额、金额与日期/编号混淆的情况，沿用 P0 的拒绝与澄清策略，不得因新增单位支持而放宽。
- 验收同时检查「`转1万给ACC-2002` 与 `转一万元给ACC-2002` 生成语义等价转账计划」，以及「`转1万5给ACC-2002` 澄清且零写入」。

#### 7.3.4 日期与金额的消歧

- 意图与槽位语法优先于数字串：`还款日`/`账单日` + `18号`/`18日` 应归一为 `repayment_day=18` 的日期槽，不生成 amount 槽；`18元` 才可作为金额候选。裸数字在没有日期名词或日期单位时不得自动当作日期。
- 校验 `1..31` 的日号范围；`0号`、`32号` 等非法值澄清。若用户未指定卡/账户且存在多张卡，先澄清目标卡，不得默认为某张卡。
- 同一句同时出现「日期数字」和「金额」时，按意图槽位分别记录；若无法区分（例如「改到18」缺少「号/日」且缺少其他上下文），应澄清而不是猜测。
- `adjust_repayment_date` 的 `new_day` 必须是整数日号，不得复用转账金额字段；确认与风险链沿用既有写操作策略。

#### 7.3.5 订阅价格变化/风险匹配与取消意图

- 订阅事实最少需支持：`subscription_id`、`merchant`、`amount_cny`、`previous_amount_cny` 或等价价格历史/风险标记、`risk_flag`、`status`、`evidence`。`涨价` 必须从可核验事实或受控历史比较得出，不能由模型自行断言。
- 目标解析顺序：用户明确 `SUB-xxxx` 或商户名精确匹配 -> 当前用户订阅中唯一「价格上涨/风险标记」匹配 -> 零或多匹配时澄清并列出候选。不得硬编码 `SUB-3002`，也不得在事实不可读时默认选演示订阅。
- 「退掉/取消」是 `cancel_subscription` 写意图，不得降级为 `list_subscriptions` 只读查询；`list_subscriptions` 只能用于「查/看看订阅」等查询表达。
- 若「那个」需要上一轮上下文才能确定，则按 P2 上下文机制处理；在没有可用上下文时澄清，不能靠模型猜测。
- 目标唯一时返回 `cancel_subscription` 计划并进入待确认/风险链；目标不唯一时返回 `needs_clarification` 且步骤为空。

#### 7.3.6 澄清与完成状态契约

目前计划层只有 `needs_clarification` 与可执行 `steps` 的布尔区分，缺少跨 Planner/API/UI 的统一状态语义。P1 应补：

- 状态机至少区分：`needs_clarification`、`draft`、`planned`、`pending_confirmation`、`executing`、`completed`、`failed`、`cancelled`。
- Planner 只能返回 `needs_clarification`、`draft` 或 `planned`；`completed` 只能在执行成功并写入审计后由执行/任务层产生。预览、澄清或空步骤绝不能被显示为 `completed`。
- 每个澄清需带稳定 `reason_code`（如 `ambiguous_card`、`missing_contact`、`ambiguous_amount`、`unsupported_category`、`ambiguous_subscription`）与候选列表；`reason_code` 用于前端文案和评测，不得只靠自然语言文案判断。
- 澄清路径必须断言业务表、待确认动作表等业务副作用为零（允许必要审计/续问记录）；前端不得把「已列出订阅/候选」显示为任务完成。

### 7.4 验收标准与建议回归/评测用例

**本节全部是验收建议，不代表任何行为已经实现，也不代表已有准确率。** 核心用例按「预期语义/计划、状态、禁止结果、副作用」定义：

| # | 用例 | 预期语义/计划 | 状态与副作用 | 必须禁止 |
|---|---|---|---|---|
| 1 | 卡丢了，帮我冻结一下 | `report_card_lost`；由尾号或唯一卡解析 `card_id` | 唯一卡时进入待确认/风险链；无唯一卡时 `needs_clarification`；澄清时零写入 | 不得默认 `CARD-8821`；不得无卡槽直接写；不得显示 `completed` |
| 2 | 我上个月在餐饮上花了多少钱 | 账单/交易查询；`period=上一自然月（Asia/Shanghai）`；`category=餐饮`；`aggregation=spend_total` | 只读；无写副作用 | 不得查询本月、不得丢掉类别或静默返回全类别、不得触发写操作 |

| 4 | 把还款日改到18号 | `adjust_repayment_date`；`new_day=18`；目标卡唯一 | 唯一卡时进入待确认/风险链；多卡或无卡时澄清；澄清时零写入 | 不得因「18」被当作金额而澄清为金额歧义；不得生成转账/金额槽；不得默认卡 |
| 5 | 给我妈转200 | 转账；`contact=妈妈`（别名归一）；`amount=200` | 唯一联系人时进入风险/确认链；零/多匹配时澄清；澄清时零写入 | 不得报「找不到联系人」、不得选错联系人、不得猜名 |

**建议的最小评测集（P1 种子集，不是 P4 的 300 条成品）：**

- 按六个表达家族各至少 4 条：1 条核心表达、1 条同义表达、1 条缺失/歧义表达、1 条安全反例；首轮不少于 24 条，并另留不少于 12 条的保留集，开发集与保留集按表达家族切分、不得近似改写泄漏。
- 具体建议用例：
  - 挂失：`卡丢了，帮我冻结一下` / `我那张尾号9902的卡丢了` / `冻结我的卡`（多卡）/ `卡丢了` + 无可核验卡（零匹配）。
  - 账单：`我上个月在餐饮上花了多少钱` / `上月吃饭花了多少` / `本月餐饮消费` / 不支持的类别或模糊时间（澄清）。
  - 金额：`转1万给ACC-2002` / `转一万元给ACC-2002` / `转1.5万给ACC-2002` / `转1万5给ACC-2002`（歧义澄清）/ `转1,500元`（仍为 1500）。
  - 还款日：`把还款日改到18号` / `还款日改到18日` / `改到0号`、`改到32号`（澄清）/ 多卡未指定（澄清）/ `改到18元`（金额与日期冲突）。
  - 联系人：`给我妈转200` / `给老妈转200` / `给母亲转200` / `给妈妈转200` / 未知或重名联系人（澄清）。
  - 订阅：`把那个涨价的订阅退掉` / `取消涨价的订阅` / 无涨价订阅（澄清）/ 多个涨价订阅（澄清）/ `查一下我的订阅`（只能只读，不能取消）。
  - 状态与安全：任何澄清/歧义/空步骤路径都不得出现 `completed`，并比较业务表与待确认表的前后快照；`不要转账，只查余额`等 P0 安全反例不得回归。

- **建议验收指标：**
  - 意图精确率、关键槽位精确匹配率（金额、日期、联系人、卡片、订阅、账期、类别）、事实来源覆盖率（每个已核验槽位必须有 `fact_source`/`fact_id`）。
  - 计划语义等价正确率（按意图、目标、参数、依赖/行为等价判断，不只比较 JSON 字符串）。
  - 澄清必要性/非必要澄清率；首次即正确率与最多一次澄清后完成率。
  - 错误完成率（`completed` 但未执行或目标错误）必须为 0；歧义/安全反例的错误写入数必须为 0。
  - 支持范围内的保留集完整计划语义正确率在建立基线后再评估；§4/P4 的「不少于 95%」仍只是候选目标，不能在本节或实现前写成成绩。
- **验收方式**：固定 Mock 数据、Planner 模式、工具目录和代码版本；同时走预览与执行入口；用快照断言澄清路径零业务写入；真实模型实验单独记录模型版本/配置与延迟成本，Mock 响应测试不能算模型理解准确率。

### 7.5 P1 已覆盖与其余阶段边界

- **P1 计划层已经提出的**：版本化 SemanticFrame 的意图列表、实体槽位、金额/时间、否定范围、条件、顺序、未覆盖片段与澄清需求；模型处理口语、确定性组件校验金额/日期/实体/来源、规则保留为基线与安全回退；从当前用户受控事实解析实体、歧义给候选而不把模型猜测当事实；用「语义契约与授权动作一致性」逐步替代旧规则写操作计数一致，并在对照评测前保留保护；对六场景未见同义表达给出语义等价计划的验收目标。
- **但 P1 还没有覆盖本节的六条具体反馈**：P1 只有框架级原则，缺少 7.3 所列的具名意图、槽位、联系人别名/卡片尾号/订阅证据事实源、混合金额与日期消歧、澄清/完成状态契约以及种子评测集。因此在完成这些修订和验收前，不能宣称六条已经由 P1 覆盖，更不能宣称已实现。
- **P2（有边界上下文与纠错）**：跨轮指代（「那个」）、缺失槽位续问（「给妈妈转钱 -> 五百」）、执行前修订（「不是500，改成300」）、会话草稿 TTL/版本、旧确认失效与跨用户隔离。若「那个涨价的订阅」依赖上一轮候选，则必须归入 P2。
- **P3（有约束组合规划）**：多意图完整编译、条件真/假/未知、类型化结果引用、写入时事实复核；本节六条原则上都是单意图，不应为了覆盖它们而提前放开任意组合或条件执行。
- **P4（效果展示）**：300 条人工标注语料、规则/LLM/新方案对照、完整指标与真实模型延迟成本、前端理解摘要与可编辑草稿。P1 的种子集不能替代 P4 保留集和正式效果报告。

### 7.6 矛盾与残余缺口

1. **P1 验收范围大于 P1 待办范围**：§4 P1 验收要求「六场景中未出现过的同义表达」语义等价，但 NLP-BACKLOG 任务 1/3 只覆盖账单查询与单笔联系人转账；挂失、还款日、订阅取消没有对应的 P1 工作项。这是当前计划最直接的范围矛盾。
2. **金额能力存在「P0 已覆盖」的隐含假设**：P0 §6 写了千/万/亿单位，但未把 `1万` 这类「阿拉伯数字 + 中文单位」单列验收；P1 又规定复用 P0 解析器。若不补显式回归，P1 的金额验收会建立在一个未被验证的假设上。
3. **事实源原则没有落到数据字段**：联系人别名、卡片尾号、订阅价格历史/`risk_flag` 都只是原则性描述；现有事实字段和计划文字之间没有一份可验收的最小字段契约，容易出现「有原则、无来源、靠模型猜」。
4. **缺少澄清/完成状态契约**：现有计划层只有 `needs_clarification` 与 steps 的布尔区分；如果前端或任务层把「列出订阅/候选」显示为 `completed`，即使语义解析正确也会产生错误的用户体验和安全误导。P1 必须把状态语义纳入验收。
5. **LLM 候选校验可能限制新表达**：P1 第 4 条提出逐步替代「必须与旧规则写操作计数一致」的上限，但待办中没有分阶段迁移任务和对照集；若直接保留旧校验，模型难以产生规则未覆盖的新意图，若直接移除又会削弱安全保护。需要独立的迁移验收。
6. **「那个涨价的订阅」的 P1/P2 边界未定**：若依赖上一轮列表/指代，应由 P2 的版本化上下文解决；若可凭当前订阅事实唯一确定，则可在 P1 单意图解决。计划必须明确按哪种输入判定，避免实现时既缺上下文又不澄清。
7. **账单类别过滤的落点未定**：`query_bill` 当前参数只有账户与账期，类别 `餐饮` 需要明确是扩展受控只读查询参数，还是在计划中记录类别并由后置结果过滤；无论哪种，都不能静默丢掉类别语义或把全类别总额当作餐饮消费。
8. **挂失是红级终态写操作**：卡片挂失需要确认/MFA、审计和不可逆语义，不能被当成普通查询或自动执行的写计划；P1 的语义草稿不能绕过既有风险、网关与执行链。
