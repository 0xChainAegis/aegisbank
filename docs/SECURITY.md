# 安全边界与生产化清单

## 当前安全设计

- **统一入口**：工具只能通过 `DagScheduler` → `PermissionGateway` 调用；没有绕过网关的 API。
- **最小权限**：工具声明 `permission`，用户可在控制台单独撤回。
- **分级确认**：green 直接执行；yellow 需确认；red 需确认 + 演示 OTP。
- **注入拦截**：网关对指令与参数做常见 Prompt 注入/越权模式检查。
- **不可抵赖审计**：审计日志包含六项核心字段，并用 SHA-256 链式串联；校验接口可发现篡改。
- **敏感信息**：仓库不包含真实银行凭证；`.env` 已被忽略，只提交 `.env.example`。

## 明确不适用于生产的部分

1. `demo-user` 是固定用户，没有登录、会话、设备绑定或真实 MFA；
2. 演示 OTP 是代码内默认值，不可用于任何生产环境；
3. 工具返回模拟账单/转账结果，没有接入银行核心或开放平台；
4. 规则注入检测只是基线，不能替代专门的安全策略引擎；
5. SQLite 单机存储不满足银行级高可用、权限隔离和 WORM 审计要求；
6. API 未做速率限制、CSRF、mTLS、细粒度 RBAC/ABAC；
7. 前端没有内容安全策略与第三方资源白名单（当前字体通过 Google Fonts 引入，离线环境可移除）。

## 上线前必须完成

- 接入银行统一身份认证、MFA 与设备指纹；
- 用 OPA/Cedar 等策略引擎替换硬编码风险判断；
- 将确认与审计写入独立、只追加、可校验的合规存储；
- 引入密钥管理服务，移除代码默认 OTP；
- 对工具输入输出做严格 schema 与金额/账户白名单校验；
- 增加速率限制、审计告警、异常熔断与人工复核；
- 通过威胁建模、渗透测试、依赖供应链扫描和数据合规评审。

## 开发约定

- 不提交 `.env`、私钥、真实账号、真实客户数据；
- 新工具必须声明风险等级、最小权限和输入/输出 schema；
- 新增工具调用路径必须经过 `PermissionGateway`；
- 修改后运行 `gate.ps1`，再通过 `checkpoint.ps1` 提交；
- 涉及公开、发布、部署时先执行 DSH 工作区的安全审计流程。
