> 制定日期：2026-10-27

> 文档性质：下一步开发建议。除明确标注为当前能力的内容外，均不得写成已完成。

## 1. 目标与边界

### 1.1 目标

1. 关闭错卡、熔断误伤、定时任务失败误报、UTC 业务日及账单口径等正确性问题。
2. 将 NLP 从“开发语料可运行”推进到“未见表达、真实模型和多轮任务可量化验收”。
3. 以最少的数据模型和接口改动，落地安全的补槽、未执行草稿修订和本人历史查询。
4. 保持并强化现有优势：确定性编译、统一网关、ActionEnvelope、幂等、执行守卫、补偿与审计。
5. 让每一项新增能力都有反例、行为断言和可复现证据，而不是只增加功能数量。

### 1.2 非目标

- 不在本轮宣称支持任意自然语言、任意条件组合或通用长期记忆。
- 不为了扩大表达覆盖而删除语义来源、候选白名单、风险、确认或执行复检。
- 本轮不实现习惯学习、个性化推荐、通用跨轮指代、任意组合/条件规划或前端偏好中心。
- 不接入真实银行、不处理真实客户资金；业务结果继续来自 Mock Bank Core。
- 不把真实身份认证、生产 MFA、OS 级沙箱和真实 IM 接入包装成赛前已经完成的能力。

## 2. 优先级与依赖

本轮只追求快速推进与落地，不设置时间表，按依赖顺序执行；能复用现有链路就不新建平台，不能以削弱安全约束换进度。

## 3. F0：问题修复与原始反例闭环

> ✅ 本工作包已于 2026-10-29 完成并合入 `main`。跨年收尾 PR [#10](https://github.com/0xChainAegis/aegisbank/pull/10) 已合并，合并提交为 `49c2f48`；完整门禁及六场景 30/30 验收通过。

### 3.1 卡片与对象解析

- [✅] 卡尾号只从当前用户的受控卡片事实中匹配；挂失、解挂、额度和还款日使用一致的对象解析口径。
- [✅] 无卡号且只有一张可选卡时，是否允许默认必须由明确产品策略决定并展示；多卡、无匹配或多匹配一律澄清。
- [✅] 移除写计划中解析失败时回落到 `CARD-8821` 等演示对象的路径。
- [✅] 保留内部卡 ID 与展示尾号的区别，确认前不得改变卡片状态。

验收反例：

1. “我那张尾号 9902 的卡挂失”只能定位当前用户的对应卡。
2. 不存在的尾号、他人卡片、重复尾号均零写入。
3. 冻结与挂失不得为了命中口语而互相替换。
4. 旧确认中的卡 ID 被替换后返回 409，且不执行。

### 3.2 熔断隔离与可用性

- [✅] 熔断计数、状态和事件按用户分桶；保留 operator 解锁与审计。
- [✅] 熔断期间合法只读查询可用，写操作继续阻断；另一个用户不被连带阻断。
- [✅] “绿色”不直接等同“只读”：具有写入或调度副作用的工具仍受熔断约束。
- [✅] 提示文案区分“当前用户写操作受限”和“服务整体未就绪”。
- [✅] API、IM、确认和后台任务使用同一判定，不新增旁路。

验收：用户 A 触发熔断后，A 的只读查询成功、写操作失败，用户 B 的合法操作不受影响；跨用户计数、冷却、解锁和重放均有回归。

### 3.3 定时任务与时间快进

- [✅] 检查脚本锁定目标任务 ID、金额、执行状态、扣款次数和失败数，不能用其他到期任务的成功代替目标任务。
- [✅] 到期时继续重新评估风险、权限和 MFA；风险升级不得绕过验证，也不得无提示地假装成功。
- [✅] 对需要补充验证的到期任务提供明确恢复路径：重新确认/MFA 或由用户重新发起；旧授权和旧 nonce 不得复用。
- [✅] `UNKNOWN` 不自动重试，进入对账；重复执行到期任务不产生第二笔扣款。

验收：`failed_count > 0`、目标金额错误、目标任务未执行或重复扣款均使场景检查失败；恢复后只执行一次。

### 3.4 业务时区与账单口径

- [✅] 数据可继续以 UTC 存储，但业务日和账期按 `Asia/Shanghai` 计算查询区间。
- [✅] 同步覆盖日累计转账、月支出、账单、定时任务及 SemanticFrame 的“今天/明天/本月”等日期解析。
- [✅] 验证北京时间 00:00–08:00、跨日、跨月及跨年边界。
- [✅] 区分消费、外部转账和本人账户内部调拨；内部调拨不重复计入消费支出，但仍按风险规则计入相应的转账统计。
- [✅] 前端只展示后端口径，不自行手减金额。

验收：内部调拨前后总资产不变、消费支出不被重复抬高；日累计风险口径不被削弱；跨零点测试有确定性的固定时钟。

## 4. U1：NLP 有界升级与独立评测前置

### 4.1 保持现有正确方向

继续使用：

```text
原始表达 + 有界会话
  → 确定性金额/日期规范化
  → SemanticFrame 候选与原文证据
  → 当前用户实体验证、缺失/歧义澄清
  → 任务完整性检查与 Plan Compiler
  → 动态风险 / 网关 / 确认 / ToolExecutor / 审计
```

模型只提交语义候选；模型自报置信度不得作为事实、授权或风险降级依据。

- [ ] 完成首批语料的正式人工复核与争议裁决关闭；当前 `human_review=pending`。

至少报告：

| 指标 | 说明 |

| 关键参数精确匹配 | 对象、金额、日期、方向等是否完全正确 |

| 漏步骤率 / 条件保留率 | 不得静默丢弃动作、否定或条件 |

“支持范围内完整计划语义正确率 ≥95%”只能作为基线后复核的目标，不能写成当前成绩。

### 4.3 评测门禁分层

- 开发回归集：必须通过，作为 CI 阻断门禁。
- 独立保留集：发布前运行并保存结果；达到约定支持范围后才转为稳定门禁。
- 开放探针：用于发现覆盖缺口，允许作为非阻断报告，但不得隐藏失败或改称全部通过。
- 真实模型评测：单独生成报告，不与离线规则或 Mock 候选混合计数。

## 5. U2：最小多轮闭环（已完成 ✅）

> 状态（2026-10-30 U2 收尾）：本轮最小范围已实现并通过专项验收；当时后端 646 项 pytest（35 个测试文件）。U4 独立回归新增 6 条后，当前全量口径为后端 652 项 pytest（36 个测试文件）、前端 144 项 Vitest（12 个测试文件）、根组装器 18 项、六场景 30/30、工具 51 个、HTTP 路径 49 个。详见 [U2 报告](../U2-CONVERSATION-2026-10-30.md) 与 [U4 交付报告](../U4-DELIVERY-2026-10-30.md)。浏览器连接真实后端的点击联调已由 U4 补齐；U1 正式人工金标与真实模型对照仍未完成。


### 5.1 只保留一条主链路

本轮仅围绕“联系人转账”打通以下流程：

1. ✅ “给妈妈转钱” → “五百”：补全当前草稿缺失的金额。
2. ✅ “不是 500，改成 300”：只修改未执行草稿的金额。
3. ✅ “我刚才转了多少 / 转给谁”：读取本人最近一次已完成转账的既有记录。

不实现任意旧轮次指代、通用“那个/刚才”解析、跨轮订阅目标选择、长期记忆摘要和已执行历史编辑。“那个涨价的订阅”如需上一轮上下文，直接留到后续；U1 的单轮处理范围不受影响。

### 5.2 最小实现方式

- [✅] 复用现有澄清续问、运行记录、Plan Compiler 和确认链，不新建通用会话平台、引用中心或时间线系统。
- [✅] 每个会话只保留一个活动草稿；最少保存 `session_id / user_id / draft_id / version / semantic_json / plan_hash / status / expires_at`，原始轮次继续关联现有 `run_id`。
- [✅] 优先扩展现有 `/api/agent/run` 与确认流程，增加 `session_id / draft_id / version` 等必要字段；历史查询复用现有运行记录并按当前用户过滤，不开放全局审计查询。
- [✅] 直接复用 U1 的 SemanticFrame 和金额解析，不另建语义模型。补槽只接受当前草稿声明的缺失金额；修订只允许 `changed_fields=[amount]`，其他改动要求重新发起。
- [✅] 复用现有状态，不做全量状态机迁移；只保证澄清、草稿和预览绝不显示 `completed`，`completed` 仍只能由执行成功后的任务层产生。
- [✅] 只补必要的稳定原因码：`missing_amount / context_expired / unsupported_amendment / draft_version_conflict`，同时提供前端所需的请求、响应和 Mock 样例。
- [✅] 会话与草稿设置固定 TTL 和长度上限；读取时发现过期即失效，清理采用现有存储能支持的最简单方式。

### 5.3 不可砍掉的安全要求

- [✅] 会话、草稿和历史查询必须按当前用户隔离；历史文本仍是不可信输入，跨轮注入不得获得额外能力。
- [✅] 补槽和修订不得继承旧授权、旧 MFA、旧 nonce 或旧确认。
- [✅] 金额修订后重新编译、生成新 `plan_hash`、重新评级并取得必要确认；旧确认执行新草稿必须返回 409。
- [✅] 草稿使用 `version` 做并发冲突检查；重复回复和重试继续使用幂等键，不得产生重复待确认动作或扣款。
- [✅] 已执行动作不能被编辑；补充回复不得新增收款人、第二个金额、额外动作或条件。
- [✅] 所有写路径继续经过网关、ActionEnvelope、ToolExecutor、SandboxGuard 和审计。

### 5.4 最小验收

- [✅] 主链路“给妈妈转钱 → 五百 → 改成三百 → 旧确认失效 → 重新确认 → 我刚才转了多少”端到端通过，最终 Mock 扣款仅为 300 元且只有一笔。
- [✅] 固定回归覆盖：他人会话、过期草稿、版本冲突、重复回复、跨轮注入、额外动作、已执行后修改；以上情况均不得产生越权或错误写入。
- [✅] 澄清、预览和旧确认不得被误报为完成；历史回读必须来自当前用户真实 Mock 执行记录，不由模型编造。
- [✅] 本轮只记录上述用例的通过/失败和失败原因，不另建多轮大规模评测平台；U1 的既定评测工作保持不变。

## 10. 完成定义（Definition of Done）

一个工作包只有同时满足以下条件才可标记完成：

- [ ] 原始反例与新增回归均通过，且断言业务状态，不只检查返回文案。
- [ ] 全量后端、前端、场景、lint、build 与安全门禁通过。
- [ ] 关键写路径仍经过网关、ActionEnvelope、ToolExecutor、SandboxGuard 和审计。
- [ ] 失败、超时、重复提交、刷新恢复、跨用户和撤权路径有测试。
- [ ] 指标附代码版本、数据划分、模型配置和测量条件。
- [ ] 文档区分当前能力、历史快照和后续目标，无未经证实的准确率或生产安全表述。
- [ ] 与产品化线完成真实联调，而不是只用 Mock 响应宣布端到端完成。
