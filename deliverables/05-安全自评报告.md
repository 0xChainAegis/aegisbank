## 0. 自评范围与口径

本报告评估的是 AegisBank **本地可运行原型**的安全设计与实现，不是生产安全认证、渗透测试报告、等保测评或合规审计结论。报告中的“已实现”均指当前代码与自动化测试可以复现的能力；“生产化建议”是上线前仍需完成的工作，不代表已经完成。

本报告使用的证据分为三类：

1. **代码证据**：`backend/aegisbank_api/` 下的网关、调度器、信任层、执行器、审计与扩展模块；

## 1. 作品与数据边界

### 1.1 作品定位

AegisBank 不是“聊天机器人 + 几个银行函数”，而是给银行 AI 智能体增加一层**金融操作控制平面**：

```text
自然语言意图
  → 结构化 Planner（只生成计划，不执行工具）
  → 确定性 Plan Compiler（Schema / DAG / plan_hash）
  → 动态风险引擎（绿 / 黄 / 红 + 可解释原因，只升不降）
  → 统一权限网关（注入拦截 / 角色能力 / 最小权限 / 分级决策）
  → 分级确认 + ActionEnvelope + 演示 MFA
  → ToolExecutor + ExecutionGuard（沙箱 / 超时 / 网络 / 体积）
  → Mock Bank Core 工具执行
  → 证据分层 + SHA-256 审计哈希链
```

它要证明的是八件事：用户能看见 Agent 准备做什么；高风险操作能被准确拦住；用户能随时撤回授权；每次放行或拒绝都有可解释原因；确认之后执行的就是用户刚刚确认的那一笔；重复提交不会重复扣款；失败与未知状态不会被伪装成成功；日志可验证且事实来源可分层。

### 1.2 数据与资金边界

| 边界项 | 当前事实 | 对外表述 |
|---|---|---|
| 银行数据 | 全部来自本地 SQLite 的 Mock Bank Core（账户、卡片、流水、订阅、理财、联系人、定时任务等），种子确定性写入 | “模拟数据，不连接真实银行系统” |
| 资金变动 | 转账、理财申购/赎回、预算锁定、礼物下单均为模拟记账，不产生真实资金结算 | “不产生真实资金变动” |
| 客户数据 | 固定演示用户 `demo-user`，联系人与账单均为虚构数据；仓库不包含真实客户数据 | “不含真实客户数据” |
| 凭据 | 仓库不包含 `.env`、私钥、真实账号或真实 API Key；`.env.example` 只列本地演示变量 | “无真实凭证” |
| 身份认证 | 无登录、会话、设备指纹或真实身份服务；固定 `demo-user` | “原型未接入真实身份认证” |
| MFA | 演示 OTP `246810`、模拟生物识别 token `FACE-888888` 为本地固定值；审批令牌为演示用途 | “演示级 MFA，不是生产 MFA” |
| 理财 | 5 个模拟产品（R1–R5）、模拟持仓与模拟收益；接口返回 `simulated=true` 与免责声明 | “模拟理财，不构成投资建议” |
| 审计存储 | 本地 SQLite 追加式审计表 + SHA-256 哈希链；可在线校验，但不是 WORM 合规存储 | “本地可验证审计，不是监管级审计存储” |
| LLM | `rule` 模式完全离线；`llm/auto` 为可选外部 OpenAI-compatible 服务，只生成候选计划 | “LLM 可选，规则 Planner 离线可用” |
| 网络 | 默认仅本机开发使用；工具执行期间沙箱做 socket 级网络阻断 | “本地演示环境，不是生产网络架构” |

### 1.3 演示 token 与最小数据原则

- 演示 OTP `246810` 只用于本地流程展示，默认值来自 `AEGIS_DEMO_OTP`，不用于任何真实环境；
- 模拟生物识别 token `FACE-888888` 硬编码在演示扩展中，只证明 Provider 协议可以端到端工作，不连接摄像头、设备传感器或真实身份服务；
- `approval_token` 是演示用确定性令牌，API 与审计只返回掩码结果（`masked()`），不作为真实授权凭证；
- 证据只存“来源 + 是否验证 + 验证方式 + 说明”，优先存哈希与结论，不存原始敏感数据；
- 密码类操作不接收、不保存、不审计明文密码，只记录 `password_changed_at`。

### 1.4 明确不做、也不对外宣称

1. 不连接真实银行核心、支付网络、征信、反欺诈或理财销售系统；
2. 不产生真实资金变动，不构成任何投资建议或收益承诺；
3. 不宣称具备生产级身份认证、生产级 MFA、OS 级沙箱、WORM 审计或高可用能力；
4. 不把“六场景 6/6 典型能力覆盖”说成“生产业务完整性”；
5. 不把“自动化测试通过”说成“人工测试完成”或“通过渗透测试”；
6. 不把本地 SHA-256 哈希链说成法律意义上的不可篡改（它只能发现记录级篡改，无法阻止拥有数据库写权限的人重算整条链）。

## 2. 权限分级实现

### 2.1 绿 / 黄 / 红三级定义

| 等级 | 定义 | 典型判定（确定性规则） | 系统行为 |
|---|---|---|---|
| 🟢 绿色 | 只读查询或低风险、无资金副作用的操作 | 账单/余额/持仓/订阅/联系人查询、账单报告、异常检测、风险测评 | 满足最小权限后直接执行，不弹确认 |
| 🟡 黄色 | 会修改账户设置、订阅状态、预算或小额动账 | 单笔转账 ≤ 5000 元且当日累计（含本次）≤ 1000 元；改还款日；额度/限额调整 ≤ 5000 元；取消订阅；虚拟卡申请/发卡；理财赎回 ≤ 1000 元；预算锁定、生日礼物预订 | 创建待确认动作，用户在有效期内确认一次后执行 |
| 🔴 红色 | 资金变动、账户安全或高风险设置 | 单笔转账 > 5000 元，或当日累计将 > 1000 元；挂失/解挂；密码重置；理财申购；理财赎回 > 1000 元；额度/限额调整 > 5000 元；定时转账 > 1000 元 | 确认 + 二次身份校验（演示 OTP 或模拟生物识别）+ ActionEnvelope 执行前复核 |

以上阈值是**确定性演示规则**，不是生产反欺诈、信用评分或监管风控模型。规则实现位于 `backend/aegisbank_api/risk.py` 与各场景模块的 `risk_rules()`；前端与接口展示的 `risk_reasons` 就是这些规则的可解释输出。

### 2.2 风险判定流程

```text
工具 Manifest 基线风险（green / yellow / red）
        │
        ▼
DynamicRiskEngine：金额、当日累计、产品风险等级、操作类型、场景规则
        │  只允许 max(基线, 动态规则)
        ▼
逐节点 RiskAssessment（level / score / reasons / requires_reauth）
        │  整条 DAG 取最高风险；红色 requires_reauth=True
        ▼
PermissionGateway.evaluate（注入 → 角色能力 → 工具授权 → 分级决策）
        │
        ├─ allow   → ToolExecutor → 工具执行 → 证据 → 审计
        ├─ confirm → 待确认动作 + ActionEnvelope → 用户确认 / MFA → 执行前复核
        └─ deny    → 整条 DAG 阻断 + gateway_blocked 审计
```

关键点：

1. 工具必须在 `BaseTool` 的 `ToolMetadata` 中声明基线 `risk_level` 与最小 `permission`；
2. 动态风险只读取确定性事实，**模型输出不参与风险判定**；
3. 场景规则按注册顺序首个命中，再与工具基线取最大值；
4. 整条 DAG 的风险取所有节点最大值；任一节点为红色，整条动作都要求二次校验；
5. 任一节点被拒绝，整条 DAG 阻断；任一节点需要确认，整条动作进入待确认，避免“执行一半再弹窗”。

### 2.3 统一网关 `gateway.evaluate` 的检查顺序

`backend/aegisbank_api/gateway.py` 是工具执行的唯一权限决策入口，检查顺序固定为：

| 顺序 | 检查 | 实现 | 失败结果 |
|---|---|---|---|
| 1 | **Prompt 注入 / 越权指令** | `scan_injection(instruction, arguments)` 扫描指令与参数 | `deny`，整条请求拒绝；调度器在 Planner 之前也会先扫描一次 |
| 2 | **角色能力** | `AuthzService.allowed(role, "tool:execute")` | `deny`；`operator` / `auditor` 不能执行银行工具 |
| 3 | **工具授权** | `PermissionStore.is_granted(user_id, tool_name)` | `deny`；撤权立即生效，提示先到权限控制台开启 |
| 4 | **风险分级决策** | 读取已评估的 `risk_level` | 绿色 `allow`；黄色 `confirm`；红色 `confirm` + `requires_reauth=True` |

补充说明：

- 风险分级本身发生在网关之前（`DagScheduler._assess_nodes`），网关消费的是已经评估过的 `RiskAssessment`，不会因为模型或调用方传入一个更低的等级而放行；
- 网关在**首次执行前**与**确认执行前**各调用一次；补偿/回滚工具执行前也会再次调用；
- `gateway.evaluate` 不直接执行工具；执行统一收口到 `ToolExecutor` + `ExecutionGuard`。

### 2.4 风险只升不降

风险引擎的核心约束是：

```text
final_level = max(tool.metadata.risk_level, dynamic_rule_level)
requires_reauth = (final_level == red)
```

- 任何模型输出都不能降低工具基线风险；
- 黄色工具可以因金额/累计/产品等级等规则升级为红色，反向不成立；
- 风险结果同时出现在 Agent 响应的 `risk`、计划步骤的 `risk_level / risk_reasons`、待确认动作、审计记录与前端风险徽标；
- `ActionEnvelope` 绑定确认时的 `risk_level`；执行前重新评估后若等级变化，直接以 `409 ENVELOPE_MISMATCH` 拒绝，不会“按新风险悄悄执行”。

### 2.5 ActionEnvelope/v1：确认绑定与执行前复算

黄色/红色操作在创建待确认动作时，为**每个计划节点**生成一份 envelope（`backend/aegisbank_api/trust/action_envelope.py` 的 `build_envelopes`）：

| 字段 | 含义 |
|---|---|
| `schema_version` | 固定 `action-envelope/v1` |
| `user_id` | 确认者身份（演示期为 `demo-user`） |
| `plan_hash` | 编译后规范化计划的 SHA-256 |
| `step_id` / `tool_name` | 绑定的计划步骤与工具 |
| `arguments_hash` | 规范化参数的 SHA-256 |
| `risk_level` / `risk_reasons` | 确认时的风险等级与原因 |
| `permission` | 工具声明的最小权限 |
| `nonce` | 一次性随机串（`uuid4().hex`） |
| `issued_at` / `expires_at` | 签发与过期时间（默认 TTL `AEGIS_CONFIRMATION_TTL_SECONDS=300` 秒） |
| `confirmation_state` | `pending / approved / rejected / expired` |
| `approval_token` | 演示审批令牌；API 与审计只返回掩码结果 |

执行前服务端按以下顺序复核（`EnvelopeService.verify`）：

1. `schema_version` 必须是 `action-envelope/v1`；
2. envelope 未过期；
3. `nonce` 未被使用；
4. `user_id` 与当前请求一致；
5. `plan_hash` 与重新编译的计划一致；
6. `step_id` / `tool_name` 与计划节点一致；
7. `arguments_hash` 与当前计划参数重新计算值一致；
8. `risk_level` 与重新评估的动态风险一致；
9. `permission` 与工具当前声明一致。

任一不一致即拒绝：**不执行、不创建业务流水**；envelope 内容不一致（版本/用户/计划/参数/风险/权限）的路径不写业务审计，过期路径会先记录状态迁移审计但仍不执行。批准或拒绝时统一 `claim_nonces` 消费 nonce，捕获重放。

### 2.6 409 语义与确认链路

| HTTP | 典型触发 | 是否执行 |
|---|---|---|
| `409 ENVELOPE_MISMATCH` | 计划哈希、参数哈希、风险等级、权限或用户身份与确认时不一致 | 否 |
| `409 ENVELOPE_EXPIRED` | 确认动作或 envelope 已过期 | 否 |
| `409 NONCE_REUSED` | 重放已消费的 nonce | 否 |
| `409 ENVELOPE_VERSION_UNSUPPORTED` | envelope 版本不受支持 | 否 |
| `409 IDEMPOTENCY_KEY_REUSED` | 同一 `Idempotency-Key` 携带不同请求体 | 否 |
| `409 IDEMPOTENCY_IN_PROGRESS` | 同一幂等键的首次请求仍在处理中 | 否 |
| `422` | 可预期业务错误（余额不足、确认后执行失败等） | 否（已失败） |
| `403` | MFA 失败、角色能力不足、未知 MFA provider | 否 |
| `503` | readiness 未就绪、沙箱执行器未装配 | 否 |
| `400` | 请求不合法、未知动作、未知演示模式 | 否 |

确认链路的实际顺序是：读取待确认动作 → 幂等重放检查 → 熔断检查 → 过期检查 → 重新评估风险 → 重算计划/校验 envelope → 拒绝或进入 MFA → 再次调用网关复检角色、权限与风险 → 状态机迁移到 `APPROVED` → 消费 nonce → 迁移到 `EXECUTING` → `ToolExecutor` 执行 → 证据与审计。确认后、执行前的复检可以拦截“等待确认期间被撤权或角色变化”的情况。

### 2.7 分级确认与演示 MFA

- **黄色**：用户在确认有效期内明确批准一次即可；不触发二次身份校验；
- **红色**：必须确认并完成 MFA；默认 provider 为 `otp`（演示 `246810`），`report_card_lost` 与 `reset_card_password` 允许 `biometric`（演示 `FACE-888888`）且推荐生物识别；
- MFA 策略由调度器强制校验允许 provider 的交集，再由 `MfaService.verify` 校验；未知 provider 返回 403；
- 成功/失败都记录 MFA 结果（provider、verification_kind、ok）；失败写 `mfa_failed` 审计并拒绝执行；
- 演示 MFA 没有失败次数锁定与速率限制，生产必须接入银行真实 MFA。

每条审计记录包含触发时间、原始指令、DAG 路径、工具入参、执行结果、用户确认状态六个核心字段，并附带 `risk_level` 与 `evidence`。

证据分层的取值固定为：`source ∈ {mock_bank, human_confirmation, policy_engine, audit_chain}`，`verified ∈ {true, false}`，`verification_kind ∈ {tool_result, approval, policy_decision, hash_chain}`。审计链按 `entry_hash = SHA-256(prev_hash + canonical(entry))` 计算，证据写入 `result_json` 并参与哈希；`GET /api/audit/verify` 全链校验，readiness 也调用同一校验。

### 4.3 残余风险结论

- **P0（R-01、R-02）** 是“不能上生产”的硬门槛：没有真实身份认证与真实 MFA，任何真实资金/客户数据都不应接入；

- **P2（R-05、R-08、R-09、R-10、R-12、R-15）** 应排期修复并纳入监控、演练与文档；
- 这些风险不影响“比赛演示与答辩”的可用性，但必须在答辩中主动说明，不能把演示级能力包装成生产能力。

## 5. 合规与对外表述

### 5.1 六场景覆盖的正确说法

赛题要求“至少覆盖 3 个核心场景，鼓励全覆盖”。当前实测覆盖 **6/6**：账单分析、卡片管理、智能转账、订阅/代扣、理财操作、跨场景联动。

准确表述是：

> “六个参考场景已完整覆盖：每类场景的典型能力可用自然语言发起，风险分级正确，审计可见，前端可展示；所有数据为模拟数据。”

不准确、不得使用的表述是：

> “六场景已达到生产业务完整性”“已接入真实银行核心”“已通过生产验收”。

### 5.2 理财合规

- 5 个产品（R1–R5）、持仓、收益、订单均为模拟数据；
- 接口返回 `simulated=true` 与免责声明；前端与文档显著标注“模拟数据，不构成投资建议”；
- 不承诺收益、不构成投资建议、不产生真实资金变动、不连接真实理财销售系统；
- 答辩与视频中不得出现“稳赚”“保本”“推荐购买”等表述。

### 5.3 数据与隐私

- 仓库不包含真实客户数据、真实账号、真实凭证或 `.env`；
- 演示用户与联系人都是虚构数据；审计证据优先存来源、验证方式与结论，不存原始敏感数据；
- 默认 `rule` Planner 完全离线；若启用 `llm/auto`，指令与参数可能发送到配置的外部 OpenAI-compatible 服务，**不得输入真实客户数据**；
- 本地 SQLite 与审计文件应按开发数据处理，不对外共享；演示结束后可重置。

### 5.4 对外表述对照表

| 可以说 | 不得说 |
|---|---|
| 本地可运行的银行 AI 智能体原型 | 已上线/已接入真实银行 |

| 演示级 MFA（OTP + 模拟生物识别） | 生产级人脸/短信/U 盾认证 |
| 进程内演示级工具沙箱 | OS 容器/微虚拟机级隔离 |
| 六场景 6/6 典型能力覆盖 | 六场景生产业务完整性 |
| 自动化测试 187/53、回归 29/29、门禁五阶段 PASS | 人工测试完成、渗透测试通过、等保合规 |

### 5.5 答辩口径建议

1. 先讲“为什么银行 Agent 需要控制平面”，再讲“我们怎么证明可信”；

### 6.3 安全机制演示路径（可复现）

以下路径用于演示，不等同于人工验收：

1. **注入整条拒绝**：向 `POST /api/agent/run` 发送含“忽略之前的指令”等文本的请求 → `status=blocked`、`risk_level=red`、`matched_rules` 非空、审计 `injection_blocked`；连续 3 次会触发注入熔断；
2. **确认绑定**：黄色/红色操作返回 `confirmation.envelopes`（掩码）；确认时若计划或参数被改，返回 `409` 且不执行；自动化用例见 `test_trust.py` 的 envelope 篡改/过期/nonce 复用；
3. **MFA**：红色操作选择 `otp` 并输入 `246810`，或选择 `biometric` 并输入 `FACE-888888`；错误 token 返回 403 并写 `mfa_failed`；
4. **熔断**：连续 3 次红色操作或 3 次注入命中后，后续写操作返回 `status=blocked`；使用 `X-Aegis-Role: operator` 调 `POST /api/trust/breaker/unlock` 解锁并写审计；
5. **沙箱**：`POST /api/sandbox/demo/run` 传 `{"kind":"network"}` / `slow` / `oversize` → `blocked=true`，对应审计 `sandbox_blocked` / `sandbox_timeout`；
6. **补偿/回退**：`POST /api/compensation/demo/run?mode=reversible` → 逆序补偿并 `rolled_back`；`irreversible` → 回滚被阻止、`unknown`；`compensation_failure` → `compensation_failed`；
7. **readiness**：`GET /api/health/ready` 非 `ready` 时，`/api/agent/run`、确认、`run-due`、IM 消息均 503；前端禁用写操作；
8. **审计链**：执行任意操作后 `GET /api/audit/verify` 仍为 `valid=true`，新增证据字段参与哈希计算。

## 7. 结论

### 7.1 赛题安全要求自评

| 赛题要求 | 自评 | 依据与说明 |
|---|---|---|
| 权限分级：绿自动 / 黄确认 / 红强验证 | ✅ 演示级满足 | 确定性风险 + 统一网关 + ActionEnvelope + 演示 MFA；P0 身份/MFA 仍需生产化 |
| 幻觉防护 | ✅ 演示级满足 | Mock 仓库为唯一事实源；Planner 只产出计划；Schema 与候选白名单；不是通用事实核查器 |
| Prompt 注入防御 | ✅ 演示级满足 | 进入 Planner 前整条拒绝；节点级再扫描；注入累计熔断；字符规则基线 |
| 完整操作审计 | ✅ 演示级满足 | 六字段 + 四类证据 + SHA-256 链 + 在线校验；不是 WORM |
| 异常熔断 | ✅ 演示级满足 | 连续失败 / 红色 / 注入三类规则；operator 解锁；系统级计数 |
| 工具运行沙箱 | ✅ 演示级满足 | 统一执行器 + 超时/网络/体积/白名单；进程内，不是 OS 隔离 |
| 中断、回退、人工接管 | ✅ 演示级满足 | 节点间暂停/恢复、逆序补偿、`UNKNOWN` 对账；不能强停执行中的工具 |
| 多角色与撤权 | ✅ 演示级满足 | `user / operator / auditor` 矩阵；撤权立即阻断；请求头不是认证 |
| 生产级安全 | ❌ 未满足 | P0/P1 风险清单明确；需真实认证、MFA、OS 沙箱、WORM、HA 等 |

### 7.2 总体结论

AegisBank 当前版本**可以用于比赛演示与答辩**：它把“自然语言 → 结构化计划 → 动态风险 → 统一网关 → 确认绑定 → 受控执行 → 证据与审计”这条信任链路做成了可运行、可测试、可复现的原型，并对高风险操作、重复提交、失败/未知状态、撤权、注入、熔断、沙箱与回滚给出了明确的工程答案。

但它**不适用于生产**：真实身份认证、真实 MFA、OS 级沙箱、HA 存储、WORM 审计、按用户熔断、TTL 清理、可取消执行等仍是硬缺口。正确的对外结论是：

> “这是一个本地可运行、自动化验证充分、边界标注诚实的银行 AI 智能体原型；它证明的是可信执行控制平面，而不是已经上线的银行系统。”

### 7.3 后续优先级

1. **P0**：真实身份认证与真实 MFA；在任何真实数据/资金接入前完成；
2. **P1**：OS 级沙箱、HA 数据库、按用户熔断、可取消执行、IM 平台签名、WORM 审计、网关限流/HTTPS；
3. **P2**：幂等/nonce TTL、前端角色单一来源、LLM 网关与数据驻留、注入分类器、补偿规格扩展；
4. **交付前**：完成阶段 2.5 人工体验回归（已推迟）、更新截图与演示视频，并在答辩材料中同步本报告的边界。

## 附录 B：术语

| 术语 | 含义 |
|---|---|
| Mock Bank Core | 确定性的本地银行数据层，所有金融事实的来源 |
| Planner | 把自然语言编译成结构化计划的组件，只产出计划 |
| Plan Compiler | 校验计划并生成规范化 `plan_hash` 的确定性组件 |
| ActionEnvelope | 绑定身份、计划、参数、风险、权限、nonce 与过期时间的一次性确认凭证 |
| 绿 / 黄 / 红 | 自动执行 / 用户确认 / 强验证三级执行策略 |
| `UNKNOWN` | 执行结果不确定的中间态，禁止自动重试，需人工对账 |
| fail closed | 依赖不可用或状态不明时默认拒绝，而非放行 |
| 证据分层 | 用 `source / verified / verification_kind` 区分数据来源与验证方式 |
| WORM | Write Once Read Many，只追加、不可改写的合规存储 |
| Dogfooding | 开发者以真实用户身份使用自家产品并记录摩擦 |
